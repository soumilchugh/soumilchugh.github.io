Agent systems · Runtime migration

Changing the agent engine without changing the product.

The decisions behind moving a production co-creator from the Claude Agent SDK to LangChain Deep Agents—while preserving tools, state, streaming, interrupts, and user-visible behavior.

01 · The real migration

An SDK replacement is really a contract migration.

The easy part was creating a Deep Agent. The hard part was preserving everything the product already expected from the old runtime.

Claude Agent SDKExisting execution runtime
→
LangChain Deep AgentsNew execution runtime
Stable contract: tools · events · history · state · interrupts · results

The migration reused a transport-neutral tool pipeline rather than rebuilding every integration. Claude remained the first model, while model construction and runtime seams stayed neutral enough for other providers to become configuration choices later.

Migration principle

Preserve product behavior at the boundary. Change the mechanism behind it.

02 · Scope

Ten decisions defined the migration.

01

Turn contract

How calls, tool events, interrupts, and the final run result correlate.

02

Conversation state

How history replays, context is summarized, and one runtime stays pinned to a conversation.

03

Usage and billing

Where provider usage enters a common accounting model, including prompt caching behavior.

04

Runtime limits

Turn caps, timeouts, retries, error translation, and production telemetry.

05

Sight and voice

How rendered images reach the model and how the agent asks the user for input.

06

Documents

How search and inspection become explicit tools after removing shell and filesystem access.

07

User context

How brand information and user-specific state enter each run safely.

08

Subagents and skills

How delegation limits tools and how eligible skills enter the prompt.

09

Evaluation

How the existing eval system measures the new path instead of silently testing the old one.

10

Cutover

When to flip the default, how to roll back, and when the old runtime can be deleted.

This list mattered because it turned a vague “port the agent” project into independently testable contracts.

03 · Architecture choices

Some features moved. Others disappeared by design.

ToolsReuse the existing dispatcher and execution pipeline behind a new adapter.One tool contract, two runtime transports.
Shell and filesDo not recreate the old sandbox. Anything previously reached through a command becomes an explicit tool. Operations requiring local paths do not belong on the new surface.Move capability into APIs, not materialized files.
SkillsRender only eligible skills into the prompt instead of writing skill files into a runtime-specific directory.Policy decides visibility; the transport only receives text.
ImagesReturn rendered images to the main agent for the current turn, then exclude image blocks from later history replay.Vision stays available without compounding image tokens.
InterruptsUse exceptions to unwind the graph for user questions and cancellation rather than adding a parallel cancellation channel.Follow the new runtime's natural control flow.
ProvidersShip Claude first, but isolate model creation, usage, caching, and configuration from the agent contract.Provider choice becomes configuration, not another migration.
04 · Dependency order

One bottleneck made the rest of the work measurable.

The turn core had to land first. Without correlated tool calls, events, history, and run results, tests could appear green while observing nothing from the new runtime.

Turn core · correlation · observable results
History + context
Runtime hardening
Vision + user input
Documents + user context
Usage + billing
Subagents + skills
Eval instrumentation
Integration gate → default flip → delete old path

The important lesson was that test observability is itself a prerequisite. A test that cannot see tool calls can pass for the wrong reason.

simpler

A flag is useful for rollout, not as a permanent architecture. Keeping both implementations indefinitely doubles the number of states the team must understand.

06 · Lessons

The durable value was in the seams, not the SDK choice.

Map behavior before code.Inventory the contracts users and tests depend on before choosing equivalents in the new runtime.
Reuse below the transport.A shared tool pipeline removes most of the migration surface and keeps behavior consistent.
Delete assumptions.Do not port a filesystem, shell, or sandbox simply because the previous SDK happened to expose one.
Test the observer.Negative assertions are meaningless when the telemetry ledger is empty.
Separate blockers from follow-ups.Explicitly accept temporary gaps such as billing drift or delayed subagents instead of discovering them during cutover.
Design the exit.The migration is complete only when the old path and its special cases are gone.
Bottom line

The migration was not one decision between two frameworks. It was ten smaller decisions about the product contract—and an order that made each one testable.
