Agent systems · Evaluation

Agent evals should explain why, not just score what.

A practical framework for turning evaluation from an outcome scorecard into a diagnostic system—one that shows what regressed, where the failure began, and what the improvement cost.

01 · The missing why

A score without attribution is only half an evaluation.

Most agent evals can tell us that one run scored lower than another. They are much less capable of telling us whether the model misunderstood the task, chose the wrong tool, received incomplete context, executed a reasonable plan badly, or produced a weak final artifact.

That distinction matters because agents are systems, not single model calls. A run combines prompts, models, context assembly, memory, tool schemas, tool implementations, state transitions, retries, infrastructure, and judges. The final score compresses all of those decisions into one number. Compression is useful for a dashboard; it is insufficient for debugging.

Hand-written scenarios create a second blind spot. They are valuable for stable coverage, but they tend to describe the workflows the team already understands. Real users discover combinations, long conversations, malformed state, and ambiguous goals that a small curated suite rarely anticipates.

Core principle

An agent evaluation system should answer three questions: Was the result good? Why did the run behave that way? Did a specific change make the system better or worse?

The goal is not simply more graders. It is an evidence chain from scenario to execution to artifact to diagnosis, with enough control to support a credible regression decision.

02 · Evaluation layers

Evaluate the run at every layer where quality can be lost.

A single end-to-end judge is important because the user experiences the final result. It should be the top of the stack, not the entire stack.

L1

Outcome quality

Did the final artifact satisfy the request? Judge correctness, completeness, visual or functional quality, constraint adherence, and usefulness against explicit criteria.

L2

Tool correctness

Was each tool call valid, necessary, correctly parameterized, and successful? Distinguish transport success from semantic success.

L3

Execution trajectory

Did the agent choose a coherent path, recover from failures, avoid loops, and stop at the right time? Evaluate observable decisions and state transitions rather than relying on the final response alone.

L4

Context and state

Did the agent receive the right history, user information, artifacts, and tool results at the moment it needed them? Missing evidence can make reasonable reasoning fail.

L5

System performance

How many tokens, tool round trips, retries, and wall-clock seconds did the task consume? Quality improvements have to be understood alongside cost and latency.

L6

Evaluator reliability

Is the signal repeatable, calibrated, covered by tests, and aligned with human judgment? An untested eval can produce precise-looking but misleading results.

03 · The run record

Diagnosis begins with recording what actually happened.

If a failed run only stores the conversation and the final score, the investigator has to reconstruct the execution from fragments. A useful run record keeps the scenario, configuration, context, calls, results, artifacts, timings, errors, and judge evidence connected by stable identifiers.

For public or production traffic, recording must be designed with privacy from the start: consent or approved use, de-identification, strict access controls, purpose-limited retention, and a clear deletion path. Raw hidden chain-of-thought is neither required nor desirable; observable actions, concise decision summaries, state transitions, and tool evidence provide a safer diagnostic record.

04 · Scenario strategy

Combine stable coverage with the shape of real work.

A healthy suite has two complementary sources. A curated set gives repeatable coverage of core capabilities and known failure modes. Traffic-derived scenarios reveal what users actually ask, including long conversations and unexpected combinations.

Curated scenarios

Small, reviewed, versioned, and tied to explicit capabilities. They become dependable smoke tests and regression anchors.

Traffic-derived scenarios

Sampled from approved telemetry, de-identified, assembled into complete task histories, and reviewed before joining the evaluation set.

Adversarial scenarios

Designed around ambiguity, missing context, tool failures, interruptions, retries, and other boundaries where the runtime must recover.

Long-horizon scenarios

Multi-turn tasks that stress memory, state, handoffs, resumability, and the compounding effects of small early mistakes.

Sampling should be explicit. Useful axes include workflow type, task length, tool mix, failure frequency, model configuration, user segment, and recency. The goal is not to mirror traffic volume exactly; it is to represent important behavior and preserve enough rare failures to learn from them.

05 · Two kinds of truth

A successful tool call and a successful outcome are different claims.

Infrastructure often marks a tool call successful when it returns without an exception. For evaluation, that definition is too weak. A call can complete yet use the wrong object, produce an empty artifact, apply a change in the wrong location, or add no value to the task.

Tool verdict

Validate schema, permissions, target, parameters, execution result, state mutation, and whether the call contributed to the plan.

Output verdict

Evaluate the final artifact against the user's intent, reference material, explicit constraints, and domain-specific quality criteria.

These verdicts should remain separate. A good output can mask wasteful or risky execution; a technically correct sequence of calls can still create a poor result. Together they narrow the search space for the failure.

06 · Trace analysis

Find the first meaningful divergence, not just the last visible defect.

Failures often surface late. The final artifact may be wrong because the agent retrieved the wrong input ten actions earlier, silently accepted an empty tool result, or carried a stale state snapshot into the next step. Trace analysis should identify the earliest decision or event that made failure likely.

A useful diagnostic view aligns the intended subgoal, observable agent decision, tool input, tool result, resulting state, and judge evidence on one timeline. It should classify likely causes—planning, context, tool selection, parameters, tool implementation, recovery, stopping, or judging—and link each claim to evidence from the record.

Analysis policy

Run expensive trace diagnosis primarily on failed, borderline, or newly regressed cases. Sample successful cases as a control so the analyzer does not learn that every trace must contain a defect.

07 · Regression gates

Make changes answerable: what moved, by how much, and in which capability?

Regression testing needs more than a before-and-after average. Each scenario should map to the capabilities and components it exercises. Baselines must be versioned. Thresholds must account for the natural variance of model and judge outputs.

Coverage map

Connect prompts, tools, runtime components, memory behavior, and model choices to the scenarios that exercise them.

Versioned baseline

Record configuration, model, judge, fixtures, environment, and suite version so a comparison can be reproduced.

Noise-aware threshold

Block on meaningful deltas, not random movement. Use repeated runs and confidence intervals where variance is material.

Owned decision

Define who updates baselines, who can approve an exception, and what evidence is required to accept a regression.

The regression gate belongs late in the build sequence. Automating an unreliable metric only makes unreliable decisions faster.

08 · Controlled comparisons

Compare models, prompts, tools, cost, and latency one variable at a time.

Agent experiments become difficult to interpret when the model, prompt, tool schema, judge, and scenario set all change together. Every comparison should declare its independent variable and freeze the rest of the configuration.

Report quality beside operational metrics: input and output tokens, cached tokens, number of model calls, tool round trips, retries, wall-clock latency, and estimated cost. Segment results by task type because a configuration that wins on short retrieval work may lose on long creative workflows.

Use the same recorded evidence for both quality diagnosis and efficiency analysis. Then a cheaper run can be understood as genuinely more efficient, rather than merely doing less work or receiving an easier scenario.

09 · Evaluate the evaluator

The eval system is production software. Test it like production software.

Filters, defaults, fixtures, data joins, rendering, and judge prompts can drift while still returning plausible numbers. That is particularly dangerous: a broken evaluator often fails silently.

Measure the noise floor

Run the same unchanged scenario and configuration multiple times. Quantify score variance, judge variance, latency variance, and failure-class stability before interpreting small deltas.

Test data and defaults

Add unit and integration tests for filters, joins, scenario assembly, missing fields, configuration inheritance, schema changes, and stale fixtures.

Calibrate judges

Compare automated verdicts with reviewed human labels, test repeated judgments, inspect disagreement, and use criteria that describe observable evidence.

Keep comparisons single-variable

Reject reports that accidentally mix changes in model, prompt, tool, judge, scenario set, or environment unless the experiment explicitly studies the combination.

10 · Implementation plan

Eight workstreams turn the framework into an operating system for quality.

01 · Scenarios from real traffic

Define privacy and sampling policy, mine approved telemetry, reconstruct complete conversations, de-identify content, review examples, and version the resulting scenario set.

02 · Complete run recording

Capture configuration, context, observable decisions, tool inputs and outputs, state transitions, artifacts, judge inputs, errors, tokens, and timings under stable run identifiers.

03 · Tool-level verdicts

Give each tool a semantic success contract. Evaluate parameter correctness, target selection, resulting state, necessity, and recovery behavior—not only whether the call returned.

04 · Output-quality evaluation

Build task-specific rubrics, references or goldens where appropriate, rendered artifact inspection, constraint checks, and calibrated automated judges with human review.

05 · Trace analysis and attribution

Align subgoals, actions, results, and state on a timeline. Find the first meaningful divergence and classify the likely cause with evidence links and confidence.

06 · Regression gates

Map code and capabilities to scenarios, create versioned baselines, establish noise-aware thresholds, report scoped deltas, and define baseline ownership and exception policy.

07 · Model, cost, and latency comparison

Run controlled experiments with one declared variable, consistent scenarios and judges, and segmented reporting across quality, tokens, calls, retries, cost, and latency.

08 · Trust in the evaluation system

Test evaluator code, fixtures, schemas, filters, defaults, and renderers. Measure repeatability and calibrate judge agreement before using the results to block releases.

11 · Execution order

Build the evidence chain before the release gate.

Establish the noise floor

Run one representative scenario repeatedly without changing the system. Learn how much movement is normal.

Harden evaluator code

Test filters, defaults, fixtures, configuration, and data contracts in parallel with the initial measurement.

Complete run recording

Make every later verdict traceable to a consistent, privacy-aware evidence record.

Add tool verdicts

Start with tools that mutate state or dominate failures, then broaden semantic success checks.

Mine realistic scenarios

Develop the telemetry pipeline alongside instrumentation and review the first traffic-derived set.

Improve output judging

Add goldens where they make sense, explicit criteria elsewhere, and calibration against human review.

Build trace attribution

Use the now-complete records and verdicts to locate the first meaningful divergence.

Enable regression gates

Only after repeatability, coverage, attribution, and ownership are strong enough to support an automated decision.

Controlled model and efficiency comparisons become useful once attribution works; otherwise a lower score or higher cost remains difficult to explain.

12 · Definition of done

What a mature eval should make possible.

After changing a prompt, model, tool, memory strategy, or runtime component, an engineer should be able to run the suite and answer:

  • Which workflows improved or regressed?
  • Was the first failure in context, planning, tool use, execution, recovery, output, or judging?
  • What trace evidence supports that diagnosis?
  • How confident are we that the movement exceeds normal variance?
  • What did the change do to tokens, cost, latency, retries, and tool round trips?
  • Can the result be reproduced from a versioned scenario and configuration?

That is the shift: from a test that says a run was bad to an evaluation system that helps the team understand, fix, and prevent the failure.
